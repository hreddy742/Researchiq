# ResearchIQ

ResearchIQ is an open-source, multi-agent market intelligence application that turns a company name or ticker into a concise investment research brief. It combines public market data, recent news, SEC EDGAR filings, local LLM sentiment analysis, and local LLM report synthesis into a streaming analyst-style workflow.

The project is designed around a simple objective: give analysts, founders, students, and builders a fast way to assemble a first-pass public company brief without paid financial data APIs or cloud LLM calls.

## Key Features

- Company or ticker search from a React dashboard
- Local ticker resolution through Ollama with fallback mappings for common companies
- Real stock quote, market-cap, valuation, volume, 52-week range, and one-year price history from Yahoo Finance through `yfinance`
- Recent headline collection from Yahoo Finance RSS and Google News RSS
- Headline-level sentiment summary using a local Ollama model
- Latest SEC 10-K lookup through the SEC EDGAR public API
- LangGraph orchestration with parallel financial, news, and filing agents
- Server-Sent Events for live agent progress updates in the browser
- Markdown-rendered investment brief generated by a local LLM
- PostgreSQL and SQLAlchemy model scaffolding for research session storage
- Docker Compose setup for local backend, frontend, and PostgreSQL

## Known Limitations

- **Research sessions are not persisted.** `GET /research/{session_id}` reads from the `ResearchSession` PostgreSQL model, but nothing in the current request flow ever writes a completed session to it — results are streamed to the client over SSE and then only live in memory. That endpoint will return `404` for any session unless a row is inserted by another process.
- **No automated test suite or CI.** There are no test files and no CI workflow in this repo yet.
- Some settings are declared but not fully wired: `MAX_NEWS_HEADLINES` and `REQUEST_TIMEOUT_SECONDS` are read from environment variables, but the news tool and individual data-source calls currently use their own hard-coded limits/timeouts instead.
- `alembic` is listed as a dependency but there's no Alembic config or migrations directory committed — schema is created via `Base.metadata.create_all` on startup, which is fine for local dev but not a substitute for real migrations.

## Architecture

```text
React + Vite
  |
  | POST /research
  | GET /research/{session_id}/stream
  v
FastAPI
  |
  v
LangGraph research workflow
  |
  +-- extract_ticker
  |
  +-- parallel_research
  |     +-- financial_agent -> yfinance
  |     +-- news_agent      -> RSS feeds + Ollama sentiment
  |     +-- filing_agent    -> SEC EDGAR
  |
  +-- report_agent -> Ollama report generation
  |
  v
SSE complete event -> frontend dashboard
```

The backend starts a background research task when `POST /research` is called. The frontend then opens an SSE connection to stream agent progress and receive the final report payload.

## Prerequisites

- Python 3.12+
- Node.js 20+
- Docker and Docker Compose, if using the containerized local workflow
- PostgreSQL, if running the backend directly without Compose
- Ollama installed locally or reachable from the backend
- The `llama3.2:3b` model, unless `OLLAMA_MODEL` is changed

Install the default Ollama model:

```bash
ollama pull llama3.2:3b
```

## Environment Variables

Copy the example file before running the backend:

```bash
cp .env.example .env
```

| Variable | Required | Default | Description |
| --- | --- | --- | --- |
| `OLLAMA_URL` | Yes | `http://localhost:11434` | Base URL for the Ollama API |
| `OLLAMA_MODEL` | Yes | `llama3.2:3b` | Model used for ticker extraction, sentiment, and report generation |
| `DATABASE_URL` | Yes | `postgresql+asyncpg://postgres:password@localhost:5432/researchiq` | Async SQLAlchemy PostgreSQL URL |
| `SEC_USER_AGENT` | Yes | `ResearchIQ research@example.com` | SEC-compliant user agent identifying your app and contact |
| `CORS_ORIGINS` | Yes | `["http://localhost:3000"]` | JSON-style list of allowed frontend origins |
| `MAX_NEWS_HEADLINES` | No | `10` | Intended news headline limit; currently the news tool uses hard-coded limits |
| `LOG_LEVEL` | No | `INFO` | Python logging level |
| `REQUEST_TIMEOUT_SECONDS` | No | `30` | Intended request timeout; currently individual tools use hard-coded timeouts |

For Docker Compose, the frontend runs on `http://localhost:4010`, the backend runs on `http://localhost:8010`, and PostgreSQL is exposed on host port `5434`. If you run the backend directly while using the Compose PostgreSQL service, set:

```bash
DATABASE_URL=postgresql+asyncpg://postgres:password@localhost:5434/researchiq
```

For the frontend, set `VITE_API_URL` in `frontend/.env.local` when the API is not running on the client default:

```bash
VITE_API_URL=http://localhost:8000
```

## Local Development

### Option 1: Docker Compose

This is the quickest way to run PostgreSQL, the backend, and the frontend together. The current Compose file expects Ollama to run on the host machine.

In one shell, start Ollama:

```bash
ollama serve
```

In another shell, pull the model and start the app:

```bash
ollama pull llama3.2:3b
docker compose up --build
```

Services:

- Frontend: `http://localhost:4010`
- Backend API: `http://localhost:8010`
- Backend health check: `http://localhost:8010/health`
- PostgreSQL: `localhost:5434`

The Compose file includes a commented Ollama service if you prefer to run Ollama in Docker. If you enable it, update the backend `OLLAMA_URL` accordingly.

### Option 2: Run Services Manually

Start PostgreSQL and create a `researchiq` database, then run the backend from the repository root:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
uvicorn backend.api.main:app --reload --host 0.0.0.0 --port 8000
```

In another shell, run the frontend:

```bash
cd frontend
npm install
npm run dev
```

Frontend default URL:

```text
http://localhost:3000
```

## API Reference

The examples below use the direct backend default `http://localhost:8000`. If you are using Docker Compose, replace it with `http://localhost:8010`.

### Health Check

```http
GET /health
```

Example:

```bash
curl http://localhost:8000/health
```

Response:

```json
{
  "status": "ok",
  "ollama": "connected",
  "model": "llama3.2:3b"
}
```

### Start Research

```http
POST /research
Content-Type: application/json
```

Request:

```json
{
  "query": "Apple"
}
```

Example:

```bash
curl -X POST http://localhost:8000/research \
  -H "Content-Type: application/json" \
  -d '{"query":"Apple"}'
```

Response:

```json
{
  "session_id": "7d62a3df-9d1e-41f0-b0d8-6bc9ecbb4f32",
  "status": "started"
}
```

### Stream Research Events

```http
GET /research/{session_id}/stream
```

Example:

```bash
curl -N http://localhost:8000/research/7d62a3df-9d1e-41f0-b0d8-6bc9ecbb4f32/stream
```

SSE event types:

| Event | Payload |
| --- | --- |
| `agent_step` | `{ "agent": "financial", "status": "complete", "output": "...", "duration_ms": 1234 }` |
| `complete` | Final stock data, news data, sentiment, report, and agent steps |
| `error` | `{ "message": "..." }` |
| `heartbeat` | Empty keep-alive payload |

Browser usage:

```ts
const source = new EventSource(`${apiUrl}/research/${sessionId}/stream`);

source.addEventListener("agent_step", (event) => {
  console.log(JSON.parse(event.data));
});

source.addEventListener("complete", (event) => {
  console.log(JSON.parse(event.data));
  source.close();
});
```

### Get Completed Research Session

```http
GET /research/{session_id}
```

This route is scaffolded to read from PostgreSQL through the `ResearchSession` model. In the current implementation, completed research results are streamed to the client but are not persisted, so this endpoint will return `404` unless rows are inserted by another process. See Known Limitations above.

## Database and Migrations

ResearchIQ uses PostgreSQL with SQLAlchemy async models. On FastAPI startup, `backend/db/database.py` calls `Base.metadata.create_all`, which creates the `research_sessions` table if it does not already exist.

Current database model:

- `research_sessions.id`
- `query`
- `ticker`
- `company_name`
- `stock_data`
- `news_data`
- `filing_data`
- `sentiment`
- `report`
- `agent_steps`
- `status`
- `created_at`

`alembic` is included in `backend/requirements.txt`, but no Alembic configuration or migration directory is currently committed. For production, add explicit migrations before relying on schema changes.
